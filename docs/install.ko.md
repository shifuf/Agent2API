# 설치와 배포

이 페이지는 세 가지 제공 형태 —— **데스크톱**(Windows / macOS / Linux), **서버**(Windows / Linux, 헤드리스), **Docker** —— 의 **전체 설치와 운영 안내**입니다. 무엇을 고를지 모르겠다면 아래 대조표를 먼저 보세요.

어느 형태든 설치 후 관리(계정 추가, 게이트웨이 키 생성, 리포트 확인)는 **브라우저 패널**에서 합니다 —— 패널은 게이트웨이와 같은 포트를 쓰고, 데스크톱 버전만 앱 창이 하나 더 있습니다.

## 채널 및 모델 설정 (이 포크)

모델 관리에서 제공자별 업스트림 모델을 조회, 가져오기, 선택 및 테스트할 수 있습니다. 공개 모델 ID, 업스트림 연결 및 선택 전략은 라우팅 그룹에서 관리합니다. 대화와 이미지 생성·편집, 멤버가 하나인 그룹도 지원합니다. 업스트림 모델을 가져오거나 활성화해도 공개 ID가 자동으로 생성되지는 않습니다.

계정 페이지와 제공자 그룹에서도 업스트림 모델을 가져올 수 있습니다. 사용자 지정 채널은 Key 그룹별로 허용 모델을 선택합니다. 계정 설정의 자격 증명 페이지에서 상세 보기를 누르면 저장된 자격 증명을 읽고 복사하거나 숨길 수 있으며 교체 입력란에는 채워지지 않습니다. 모바일 계정 상세 화면에서도 사용할 수 있습니다. 관리자 세션 또는 환경 변수 관리 Key가 필요하며 일반 게이트웨이 Key는 읽을 수 없습니다. 숨기기, 페이지 전환 또는 닫기를 하면 표시 내용이 지워집니다.

1. 계정 페이지에서 「사용자 지정 채널 추가」를 누르거나 계정 추가 → API 템플릿으로 들어가 API 제공자 또는 템플릿을 선택하고 API 주소와 이름 있는 Key 그룹을 설정합니다. 그룹마다 여러 키를 등록할 수 있으며 Key와 「지원 모델」은 별도 영역에서 관리합니다. 모델을 선택하지 않고 채널을 먼저 저장한 뒤 나중에 설정할 수 있습니다. 그룹별로 모델을 가져오거나 「모든 그룹의 모델 가져오기」를 실행한 후 모델을 선택하고 확인하세요. 목록을 가져와도 자동으로 선택되지 않으며, 모델이 없거나 비활성화된 그룹은 요청을 전달하지 않습니다.
2. 라우팅 → 그룹 만들기에서 이름과 공개 모델 ID를 입력하고 대화 또는 이미지를 선택합니다. 계정 제공자별로 가져온 업스트림 모델과 참여 계정을 선택하세요. 단일 모델은 멤버 하나로, 여러 채널은 여러 멤버와 전략으로 구성합니다. 공개 ID는 업스트림 ID와 같아도 되며 저장된 그룹만 이름을 점유합니다. 멤버와 중첩 그룹의 유형은 같아야 합니다.
3. 게이트웨이 Key의 생성, 편집, 조회와 사용 범위 설정은 별도로 진행합니다. 목록의 「사용 가능 범위」에서 허용 채널과 공개 모델을 각각 선택하세요. 선택 패널은 검색, 선택 항목 미리보기 및 확인을 지원합니다. 두 항목을 모두 설정하면 두 제한이 동시에 적용됩니다. 채널 미선택은 모든 채널, 모델 미선택은 모든 공개 모델을 허용합니다. 채널을 삭제해도 기존 Key 제한은 유지됩니다.
4. 프록시 페이지에서 구독을 관리하고 코어를 설치하거나 가져옵니다. 구독 노드는 계정 및 프록시 풀에서 사용할 수 있습니다. 코어를 중지하거나 노드를 비활성화해도 연결된 요청이 직접 연결로 전환되지 않습니다.

채널은 중앙 폼, Key 편집과 모델 선택은 옆 패널에서 관리합니다. 후보에는 활성화되어 있고 자격 증명과 모델 사용 권한이 있는 계정만 표시됩니다. 클라이언트와 게이트웨이 Key에는 사용 가능한 업스트림이 있는 활성 그룹만 표시합니다. 사용 불가능해진 기존 Key 제한은 유지하며 권한을 확대하지 않습니다.

### 업그레이드 시 라우팅 이전

업그레이드 전에 컨테이너를 중지하고 데이터베이스와 계정 암호화 키를 포함한 전체 데이터 디렉터리를 백업하세요. 첫 실행에서 기존 모델과 독립 경로를 그룹으로 원자적으로 이전하며 공개 ID의 대소문자, 활성 상태, 계정 범위, 전략을 유지합니다. 공개 모델에 대응하지 않는 경로는 비활성 초안으로 전환합니다. 원래 설정은 데이터베이스 설정 항목 `routingGroupsMigrationV1`에 보존하며 계정과 게이트웨이 Key는 변경하지 않습니다. 재시작해도 이전을 반복하지 않습니다. 손상이나 이름 충돌이 있으면 명확한 오류와 함께 이전을 중지하고 기존 설정을 보존합니다. 이전 프로그램으로 되돌릴 때는 업그레이드 전 전체 백업을 복원하세요.

라우팅 화면은 개발사를 식별하고 여러 채널의 동일 모델을 그룹으로 제안합니다. 제안은 기본적으로 공개되지 않습니다. 자동 그룹을 명시적으로 켜거나 사용자 지정 그룹을 저장하고 활성화하세요. 숨기기, 복원, 복사, 정렬, 가져오기와 내보내기를 지원합니다. 복사와 가져오기로 만든 그룹은 기본적으로 비활성화됩니다. 내보내기에는 계정 ID와 로컬 디렉터리 조건이 있는 규칙이 포함되지 않습니다. 가져온 후 채널과 계정 범위를 확인하세요.

순서, 순환, 스마트, 최소 사용량, 소비 속도, 무료, 속도, 가중치, 수동, 공급자 우선 전략을 지원합니다. 구성원은 선택한 계정이나 채널의 모든 계정을 사용하며 중첩 그룹과 모델 패턴도 지원합니다. 규칙에는 token 수, 이미지, 추론 수준, 클라이언트, 의도, 압축 요청, 시간대, 디렉터리를 지정합니다. 의도와 자동 추론 수준에는 분류기가 필요하며 추가 업스트림 호출이 발생합니다. 시간 초과나 잘못된 결과는 일반 라우팅으로 돌아갑니다.

미리보기는 요청 조건, 일치한 규칙, 우선 후보와 제외 이유를 표시하며 요청을 보내거나 순환 상태를 바꾸지 않습니다. 첫 콘텐츠 시간 초과는 출력 전까지만 업스트림을 전환하며 엄격한 고정은 계정을 바꾸지 않습니다. 새 그룹은 일시적 오류 대기 시간을 설정할 수 있고 기존 그룹의 대기 동작은 유지됩니다. 모바일에서는 「더 보기 → 라우팅」을 엽니다. 비활성화되거나 사용 가능한 계정이 없는 그룹은 클라이언트와 Key 모델 목록에 표시되지 않으며 Key의 모델 및 채널 제한은 항상 적용됩니다.

순서 우선은 사용 가능한 첫 구성원을 시도하고 폴백 가능한 실패가 발생해야 다음 구성원으로 넘어갑니다. 요청마다 모든 구성원에 순서대로 분배하는 설정은 아닙니다. 업스트림이 HTTP 200을 반환한 뒤 유효한 내용을 보내지 않으면 첫 콘텐츠 제한 시간을 설정하세요(예: 20초). 0은 제한을 끄므로 클라이언트 연결이 끊길 때까지 기다릴 수 있습니다. 일시적 실패 대기 0은 실패 후 60초의 재시도 예산이며, 각 구성원의 첫 콘텐츠 제한 시간이 아닙니다. 매번 첫 구성원부터 시도하려면 세션 고정을 끄고, 요청마다 구성원을 바꾸려면 순환 전략을 사용하세요. 콘텐츠 출력이 시작되면 업스트림을 바꾸지 않습니다.

사용 중인 기기에 맞는 행을 고르세요:

| 형태 | 산출물 | 인터페이스 | 설명 |
| --- | --- | --- | --- |
| **Windows 데스크톱**(권장) | `Agent2API_<버전>_x64-setup.exe` | 앱 창 | NSIS 설치 프로그램, 기본 설치 경로 `C:\Program Files\Agent2API`, 설치 시 관리자 권한 필요 |

| **Windows 서버** (GUI 없음) | `agent2api-server-windows-amd64.zip` | **브라우저 패널** | 명령줄로 설치하고 Windows 서비스로 등록 —— [서버](#서버windows--linux-헤드리스) 참고 |
| **Linux 서버** (GUI 없음) | `agent2api-server-linux-<arch>.tar.gz` | **브라우저 패널** | 명령줄로 설치하고 systemd 로 상주. 같은 패키지가 컨테이너 내 업데이트 페이로드도 겸합니다 |
| **Docker** | `ghcr.io/shifuf/agent2api:latest` | **브라우저 패널** | amd64 / arm64 이미지, [Docker 배포](#docker) 참고 |

> 무엇을 고를까: **데스크톱이 있다**(트레이, 부팅 시 자동 시작, 본机 로그인 상태 가져오기가 필요) → 데스크톱 버전.
> **서버에 그래픽 인터페이스가 없다**(Windows Server / Linux 서버) → 서버 패키지.
> **이미 Docker 를 돌리고 있다** → 이미지.
>
> 데스크톱 버전은 그래픽 세션이 필요하며 **헤드리스 서버에는 설치할 수 없습니다**.
> 서버 패키지는 WebView / GTK 에 전혀 링크하지 않고, 실행 파일 하나와 `ui/` 디렉터리만 있으면 됩니다.

## 데스크톱(Windows / macOS / Linux)

**데스크톱**(Windows / macOS / Linux)은 설치 후 그냥 실행하면 됩니다. **Node나 다른 런타임이 필요 없으며**, 게이트웨이는 앱 프로세스 안에서 돌고 트레이에 상주합니다.

1. 첫 실행 시 앱 프로세스 안에서 로컬 게이트웨이(포트 3065)가 시작되고 메인 창이 열립니다. 이전 버전의 데이터 디렉터리나 데이터 파일이 발견되면 마이그레이션 안내 대화상자가 표시되며, 안내에 따라 진행하면 됩니다.
2. "계정" 페이지에서 "계정 추가"를 누르고 프로바이더를 고른 뒤, 대화상자 안내대로 로그인하거나 자격 증명을 입력하면 됩니다(웹 로그인 / SMS 인증 코드 / 자격 증명 붙여넣기 / 이 PC 로그인 상태 가져오기).
3. OpenAI 클라이언트의 `base_url`을 `http://127.0.0.1:3065/v1`로 설정하고 `api_key`는 아무 값이나 넣으면 됩니다(예: `sk-local`. 인증을 켜지 않으면 서버는 검사하지 않습니다).

창을 닫아도 기본적으로 트레이로 최소화될 뿐이며 게이트웨이는 백그라운드에서 계속 전달합니다. 완전히 종료하려면 트레이 아이콘을 오른쪽 클릭해 "종료"를 선택하세요.

> **macOS 첫 실행**: dmg 안의 앱에는 Apple 코드 서명과 공증이 적용되지 않았습니다(서명에는 유료 Apple Developer 계정이 필요합니다. `.github/workflows/build.yml` 설명 참고). 따라서 Gatekeeper가 첫 실행을 차단하며, "시스템 설정 → 개인정보 보호 및 보안"에서 한 번 수동으로 허용하면 됩니다.
>
> **Linux 데스크톱**: 트레이는 `libayatana-appindicator3`가 필요합니다(대부분의 데스크톱 환경에 포함). 아이콘이 보이지 않으면 `libayatana-appindicator3-1`을 설치하고 다시 실행하세요. AppImage는 첫 실행 전에 실행 권한이 필요합니다(`chmod +x`, "설치 프로그램 열기"를 선택하면 자동으로 부여됩니다). 업데이트: deb는 시스템 설치 프로그램을 거치고(설치 시 비밀번호를 한 번 묻습니다), AppImage는 파일을 교체하면 업그레이드됩니다.
>
> **데스크톱 버전의 차이**: AutoClaw와 智谱清言의 "이 PC 로그인 상태 가져오기"는 Windows에서만 사용할 수 있습니다(Windows DPAPI 암호문을 읽기 때문에 macOS / Linux에서는 해당 섹션이 숨겨집니다). 나머지(小浣熊 / CatPaw / Cline)는 `HOME` 아래 평문 파일을 읽으므로 세 플랫폼 모두에서 사용할 수 있습니다. 트레이, 자동 시작, 네트워크 접근, 웹 패널 호스팅은 macOS / Linux에서도 동일하게 지원됩니다.

## 서버(Windows / Linux, 헤드리스)

**그래픽 인터페이스가 없는 서버**(Windows Server, Linux 서버, 클라우드 인스턴스)용입니다. 산출물은 모두 같은 `agent2api-server` 바이너리로, 창도 트레이도 없고 WebView / GTK 에 링크하지 않으며 실행 시 Node 나 다른 런타임이 필요 없습니다. 명령은 **설치만** 담당하고, 그 이후의 관리(계정 추가, 키 생성, 리포트 확인)는 모두 브라우저 패널에서 합니다.

서비스는 시스템 서비스로 상주합니다: 부팅 시 자동 시작, 크래시 후 자동 재시작, 콘솔 없는 백그라운드 실행.

### Windows Server

`agent2api-server-windows-amd64.zip` 를 내려받아 압축을 풀고 **관리자 권한으로** PowerShell 을 엽니다:

```powershell
Expand-Archive agent2api-server-windows-amd64.zip -DestinationPath C:\agent2api-pkg
cd C:\agent2api-pkg
.\install-service.ps1
```

스크립트는 프로그램을 `C:\Agent2API` 에, 데이터를 `C:\ProgramData\Agent2API` 에 넣고, `Agent2API` 라는 Windows 서비스(`LocalSystem`, 부팅 시 자동 시작)를 등록하고 방화벽 인바운드 규칙을 추가한 뒤 서비스를 시작합니다.

```powershell
# 위치와 포트 지정
.\install-service.ps1 -InstallDir D:\apps\agent2api -DataDir D:\data\agent2api -Port 8080

# 일상 관리
Get-Service Agent2API
Restart-Service Agent2API
Stop-Service Agent2API

# 제거(데이터 유지). -Purge 를 붙이면 프로그램과 데이터를 함께 삭제
.\install-service.ps1 -Uninstall
```

**원클릭 업데이트**: 표준 Windows 서비스는 설정 → 업데이트에서 원클릭 업데이트를 제공합니다. 확인 후 Windows x64 서버 패키지를 다운로드하고 공식 해시를 독립적으로 검증합니다. 임시 업데이트 프로세스가 서비스를 중지하고 파일 점유가 풀릴 때까지 기다린 후 백업·교체·재시작합니다. 새 버전 실행 확인 후 페이지가 새로 고쳐지며 계정, 설정 및 데이터는 유지됩니다.

**이전 설치 연결 / 수동 업그레이드**: 새 패키지를 새로운 폴더에 풀고 관리자 권한으로 `install-service.ps1`을 한 번 실행하세요. 등록된 설치·데이터 경로, 포트, 환경 설정 및 서비스 계정을 기본적으로 보존합니다. 포트처럼 명시한 옵션만 변경하며 디렉터리 이전은 별도로 진행합니다. 이후에는 패널에서 업데이트할 수 있습니다.

프로그램은 SYSTEM과 관리자만 쓸 수 있으며 작업 폴더는 `<설치 폴더>\.service-update`입니다. 상주 서비스는 추가하지 않습니다. 서비스 환경의 `AGENT2API_WINDOWS_UPDATE=0`으로 기능을 끌 수 있습니다. 사용자 지정 계정, 디렉터리 링크, 네트워크 경로 및 외부 작업 그룹 관리 환경은 자동 권한 상승 없이 수동으로 업그레이드합니다. 교체 실패 시 이전 파일을 복원하고 새 버전 시작 실패 시 로그와 백업을 남기며 데이터베이스를 자동으로 되돌리지 않습니다.

> **Windows 특유의 함정 두 가지는 스크립트가 이미 처리합니다**:
> 서비스 프로세스의 작업 디렉터리는 exe 가 있는 폴더가 아니라 `C:\Windows\system32` 입니다 —— UI 디렉터리는 exe 경로로 찾으므로 영향이 없습니다. 데이터 디렉터리는 서비스 레지스트리의 `AGENT2API_PROXY_HOME` 에 명시적으로 기록합니다(설정하지 않으면 LocalSystem 의 `C:\Windows\system32\config\systemprofile` 아래로 떨어져 찾기 어렵습니다).
> 서비스에는 콘솔이 없으므로 로그는 파일 `C:\ProgramData\Agent2API\logs\server.log` 에도 남습니다.

### Linux (systemd)

```bash
tar -xzf agent2api-server-linux-amd64.tar.gz
cd agent2api-server-linux-amd64      # 압축을 푼 디렉터리 이름에 맞추세요
sudo bash install.sh
```

스크립트는 `agent2api` 시스템 계정(로그인 불가)을 만들고, 프로그램을 `/opt/agent2api` 에, 데이터를 `/var/lib/agent2api` 에, 설정을 `/etc/agent2api/agent2api.env` 에 두고 systemd 유닛을 `enable + start` 합니다.

```bash
# 업그레이드(데이터와 설정은 유지, 이전 바이너리는 .bak 으로 백업)
sudo bash install.sh --upgrade

# 제거(데이터 유지). --purge 를 붙이면 데이터와 설정을 함께 삭제
sudo bash install.sh --uninstall

# 일상 관리
systemctl status agent2api
systemctl restart agent2api
journalctl -u agent2api -f
```

부팅 시 자동 시작, 크래시 후 자동 재시작(`Restart=always`), SIGTERM 우아한 종료(처리 중인 요청을 기다린 뒤 끝나므로 SSE 장기 연결이 끊기지 않습니다)가 모두 설정되어 있습니다. `/etc/agent2api/agent2api.env` 를 수정했다면 `systemctl restart agent2api` 로 반영합니다.

> **systemd 원클릭 업데이트**: 표준 설치에는 제한된 업데이트 프로그램이 포함됩니다. 패널에서 업데이트를 확인하면 다운로드, 공식 체크섬 독립 검증, 백업 및 교체, 재시작과 새 서비스 확인까지 수행합니다. 계정과 설정은 유지되며 게이트웨이는 일반 계정으로 실행되고 프로그램 파일은 root 소유로 보호됩니다.
>
> 이전 설치는 이 기능을 포함한 새 서버 패키지를 받아 해당 폴더에서 `sudo bash install.sh --upgrade`를 한 번 실행해 구성 요소를 설치하세요. 사용자 지정 서비스 계정이나 경로는 덮어쓰지 않으므로 기존 배포 절차를 사용하세요. `AGENT2API_SYSTEMD_UPDATE=0`으로 패널 기능을 끄거나 `agent2api-updater.socket`을 비활성화해 업데이트 구성 요소를 끌 수 있습니다. `AGENT2API_SELF_UPDATE`는 여전히 Docker 전용입니다.
>
> 업데이트 프로그램은 로컬 socket을 사용하며 네트워크 포트를 열지 않습니다. 출시 정책과 검증 정보는 공식 웹사이트에서만 가져옵니다. 독립 검증에 프록시가 필요하면 `/etc/agent2api/updater.env`에 `HTTPS_PROXY`를 설정할 수 있습니다. 교체 실패 시 이전 파일을 복구합니다. 새 서비스 시작을 확인하지 못하면 `/opt/agent2api/.before-update-*`에 복구 파일을 남기고 실패를 알리며 데이터베이스를 자동으로 되돌리지 않습니다.

### 설치 후

두 플랫폼 모두 같습니다 —— 브라우저를 엽니다:

```
http://<서버IP>:3065/
```

1. 첫 방문에서 **관리자 계정 등록**을 안내합니다(환경 변수로 미리 설정할 수도 있습니다. 아래 참고)
2. 로그인 후 "게이트웨이 키" 페이지에서 API 키를 만듭니다
3. 클라이언트 `base_url` 을 `http://<서버IP>:3065/v1` 로, `api_key` 를 방금 만든 키로 설정합니다

> ⚠️ **키를 만들기 전에는 `/v1/*` 가 서비스를 거부합니다**(fail-closed). 의도된 동작입니다. 서버 형태는 `0.0.0.0` 에 바인딩하므로, 키 없이 업스트림 쿼터를 네트워크 전체에 여는 건 받아들일 수 없습니다.

### 무인 배포

관리자와 게이트웨이 키 모두 환경 변수로 미리 설정해 브라우저 수작업을 건너뛸 수 있습니다:

| 변수 | 설명 |
| --- | --- |
| `AGENT2API_ADMIN_USER` + `AGENT2API_ADMIN_PASSWORD` | 관리자 미리 설정(비밀번호는 평문으로 입력, 시작 시 bcrypt 로 변환). `AGENT2API_ADMIN_PASSWORD_HASH` 로 완성된 해시를 줄 수도 있습니다 |
| `AGENT2API_PROXY_API_KEY` | 게이트웨이 키를 하나 미리 설정해 "패널에서 첫 키 만들기"를 건너뜀 |
| `AGENT2API_PROXY_HOME` | 데이터 디렉터리 |
| `AGENT2API_HOST` / `AGENT2API_PROXY_PORT` | 수신 주소(기본 `0.0.0.0`) / 포트(기본 `3065`) |
| `AGENT2API_PANEL_PORT` | 패널을 별도 포트로 분리: 관리 플레인이 그 포트에서 수신하고 주 포트는 `/v1/*` 만 제공 |
| `AGENT2API_ALLOW_NO_KEY` | `1`이면 fail-closed 해제(순수 내부망 한정) |
| `AGENT2API_LOG_FILE` | 로그 파일 경로, 기본 `{데이터 디렉터리}/logs/server.log` |
| `AGENT2API_VERBOSE` | `1`이면 debug 로그 활성화 |

Linux 에서는 `/etc/agent2api/agent2api.env` 에, Windows 에서는 서비스 레지스트리 키 `HKLM\SYSTEM\CurrentControlSet\Services\Agent2API\Environment` 에 적습니다(`install-service.ps1` 이 기본 항목을 기록하며, 다시 실행할 때는 기존 설정을 유지하고 매개변수로 명시한 항목만 변경합니다).

> **계정은 미리 설정할 수 없습니다**: 계정에는 QR 스캔 / SMS 코드 / 자격 증명 붙여넣기가 필요하고 이는 업스트림 프로토콜이 정하는 부분이라 우회할 수 없습니다. 대량 배포에서는 이미 설정한 **데이터 디렉터리를 통째로 복사**하세요(SQLite 데이터베이스와 `account.key` 가 같은 디렉터리에 있어 계정도 함께 옮겨집니다).

**Trae 응답 완전성 검사(데스크톱 / 서버 / Docker)**: 기본적으로 켜져 있습니다. 호환성으로 인한 오탐을 조사할 때만 게이트웨이 프로세스 환경에 `AGENT2API_TRAE_NO_REQUIRE_TERMINAL=1`을 설정하고(`true` / `yes` / `on`도 허용), 게이트웨이를 재시작해 플러그인이 새 환경을 상속하게 하세요. 끄면 업스트림의 완료 신호가 없는 불완전한 응답을 다시 성공으로 처리할 수 있습니다. 변수를 제거하고 재시작하면 검사가 복원됩니다. 이 설정은 해당 수정이 포함된 제공자 플러그인이 필요합니다.

## Docker

이 fork는 `ghcr.io/shifuf/agent2api`에 이미지를 게시합니다. `main`에 push하면 `latest`, `beta`에 push하면 `beta`가 갱신됩니다. 각 빌드는 버전 고정용 `sha-<전체 커밋 SHA>`도 게시합니다. Actions의 **Docker package**를 수동 실행하면 main/beta는 해당 태그를, 다른 브랜치는 `dev`만 갱신합니다. amd64 / arm64를 지원하며 데스크톱, 로그인, 모바일 UI와 번역을 소스에서 다시 빌드합니다.

워크플로는 현재 저장소의 `GITHUB_TOKEN`으로 GHCR에 게시하므로 Docker Hub 또는 상위 빌드 저장소 자격 증명이 필요 없습니다. 다른 fork에서는 경로가 소문자 `ghcr.io/<소유자>/<저장소>`로 자동 변경됩니다. Actions를 활성화하고 코드를 push한 다음 **Actions → Docker package**에서 결과를 확인하세요. 첫 게시 후 익명 pull을 허용하려면 패키지 공개 범위를 Public으로 변경하세요. 컨테이너 패키지만 게시하며 Git tag / GitHub Release를 만들거나 버전 번호를 변경하지 않습니다.

저장소의 Compose 파일은 `AGENT2API_IMAGE`(기본 `ghcr.io/shifuf/agent2api`)와 `AGENT2API_VERSION`(기본 `latest`)을 지원합니다. 이미지 선택에만 사용되며 앱에는 전달하지 않습니다. 가져오기 및 배포:

```bash
docker compose up -d --pull always --no-build
AGENT2API_VERSION=beta docker compose up -d --pull always --no-build
```

```bash
docker run -d --name agent2api --restart unless-stopped \
  -p 3065:3065 -v ./data:/data \
  ghcr.io/shifuf/agent2api:latest
```

브라우저에서 `http://<호스트>:3065`를 열면 첫 방문 시 **관리자 계정 등록**으로 안내합니다. 로그인 후 "게이트웨이 키" 페이지에서 클라이언트용 API 키를 만들면 됩니다 — `http://<호스트>:3065/v1`이 OpenAI 호환 엔드포인트이며, 키를 만들기 전에는 전달을 거부합니다. 모든 상태(SQLite 데이터베이스 / 설정 / 로그)는 `./data` 볼륨 하나에 저장됩니다.

compose 사용자용(amd64 / arm64 이미지 모두 제공):

```yaml
services:
  agent2api:
    image: ghcr.io/shifuf/agent2api:latest
    container_name: agent2api
    restart: unless-stopped
    ports:
      - "3065:3065"
    volumes:
      - ./data:/data
```

환경 변수(모두 선택 사항):

| 변수 | 설명 |
| --- | --- |
| `AGENT2API_ADMIN_USER` + `AGENT2API_ADMIN_PASSWORD` | 관리자 계정과 비밀번호 사전 설정(비밀번호는 평문으로 입력, 시작 시 자동 해시). 미설정 시 패널에서 등록 |
| `AGENT2API_PANEL_PORT` | 패널을 별도 포트로 분리: 설정하면 패널(UI + `/api/*`)이 해당 포트만 수신하고, 공개 측에는 메인 포트만 매핑해 관리 표면을 내부에 둘 수 있습니다(패널 포트는 루프백에 바인딩. `127.0.0.1:3066:3066`처럼 기재) |
| `AGENT2API_HOST` / `AGENT2API_PROXY_PORT` | 수신 주소(기본 `0.0.0.0`) / 포트(기본 `3065`) |
| `AGENT2API_ALLOW_NO_KEY` | `1`이면 fail-closed 해제(키 미설정이어도 `/v1` 허용, 순수 내부망 한정) |
| `AGENT2API_CAPTCHA_ENABLED` | 로그인 페이지 사람 확인 위젯: 기본 `1`(켜짐), `0`은 끔 |
| `AGENT2API_SELF_UPDATE` | 컨테이너 내부 업데이트: 이 fork의 기본값은 `0`이며 Compose로 자신의 이미지를 가져와 업데이트합니다. `1`로 활성화하기 전에 자신의 Release 소스를 설정하세요 |
| `AGENT2API_IMAGE_CACHE_MB` | 생성 이미지의 다운로드 메모리 캐시 상한(MiB, 기본 `128`, 범위 8~4096). 잘못된 값 / 범위 밖은 기본값으로 폴백 |
| `AGENT2API_IMAGE_COMPRESS_CACHE_MB` | 세션 이미지 압축 결과의 메모리 캐시 상한(MiB, 기본 `128`, 범위 8~4096, 기준 동일) |

소프트웨어와 플러그인의 버전 확인 및 설치 파일 다운로드는 [Agent2API 공식 웹사이트](https://agent2api.dev/downloads)만 사용합니다. 사용자 지정 업데이트 소스와 GitHub 가속 소스는 더 이상 지원하지 않으며 GitHub 토큰도 필요하지 않습니다. 공식 웹사이트 연결에 사용할 프록시는 업데이트 설정에서 선택할 수 있습니다.

소스에서 빌드하려면 저장소를 clone하고 `docker compose up -d --build --pull never`를 실행하세요. Dockerfile은 lock 파일로 의존성을 설치하고 UI를 다시 빌드합니다. 최종 이미지는 게이트웨이와 패널만 포함하며 Node / Rust 도구 체인은 포함하지 않습니다.

### 업스트림 컨테이너에서 이 fork로 이전

이 fork의 **Docker package** 빌드가 성공하고 대상 `sha-<40자리 전체 커밋 SHA>` 이미지를 pull할 수 있는지 확인한 뒤 진행하세요. 저장소에 워크플로 파일이 있다고 이미지가 게시된 것은 아닙니다. 아래 예시는 Linux에서 `docker run`으로 만든 `agent2api`, 포트 `3065:3065`, `AGENT2API_PROXY_HOME=/data`, bind mount `/www/server/panel/data:/data`를 가정합니다. 실제 마운트를 먼저 확인하고, 현재 디렉터리로 이전 `./data` 경로를 추측하지 마세요:

```bash
docker inspect --format '{{.Config.Image}}{{println}}{{range .Mounts}}{{println .Type .Source "->" .Destination}}{{end}}' agent2api
```

`agent2api.db`, 존재하는 `-wal` / `-shm`, `account.key`, `update-token.key`, `cloud-sync.key`, 플러그인과 기존 설정을 포함해 데이터 디렉터리 전체를 보존하세요. 기존 컨테이너에 `AGENT2API_ACCOUNT_KEY`가 설정되어 있다면 정확히 같은 값을 유지해야 합니다. 유효한 환경 키가 `account.key`보다 우선하므로 새 키로 교체하지 마세요. 아래 명령은 이 변수만 보호된 파일에 저장하며 터미널에는 표시하지 않습니다. 다른 사용자 지정 환경 변수, 포트, 네트워크와 추가 마운트도 유지하세요.

새 컨테이너는 별도 디렉터리의 사본을 사용하고 원본은 기존 컨테이너용으로 남깁니다. `/www/server/panel/data`가 서버 관리 패널의 데이터 디렉터리일 수도 있으므로 전체를 이동하거나 덮어쓰거나 비우지 마세요. 다른 파일도 사본과 백업에 포함될 수 있으니 이전 디렉터리와 키 파일을 민감한 백업으로 보호하세요. 서버의 **root Bash**에서 이미지 자리표시자를 바꾼 뒤 실행합니다. 이미지를 먼저 pull하고 기존 컨테이너를 중지한 다음 복사와 압축 없는 아카이브를 진행합니다. 어느 단계든 실패하면 중단합니다. 사본과 아카이브 공간이 필요하며, 중단 시간에는 복사, 백업 및 새 버전 시작 시간이 포함됩니다.

```bash
set -euo pipefail
umask 077
NEW_IMAGE='ghcr.io/shifuf/agent2api:sha-<PUBLISHED_FULL_40_CHARACTER_SHA>'
SOURCE_DATA='/www/server/panel/data'
test "$(docker inspect --format '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Source}}{{end}}{{end}}' agent2api)" = "$SOURCE_DATA"
test -d "$SOURCE_DATA"
docker pull "$NEW_IMAGE"

STAMP=$(date +%Y%m%d-%H%M%S)
MIGRATION_DIR="/opt/agent2api/migrations/$STAMP"
FORK_DATA="$MIGRATION_DIR/data"
OLD_CONTAINER="agent2api-before-fork-$STAMP"
test ! -e "$MIGRATION_DIR"
mkdir -p "$FORK_DATA"
chmod 700 "$MIGRATION_DIR"
printf '%s\n' "$OLD_CONTAINER" > "$MIGRATION_DIR/old-container-name.txt"
docker inspect --format 'container={{.Id}} image={{.Config.Image}} imageId={{.Image}}' agent2api > "$MIGRATION_DIR/container-image.txt"
docker inspect --format '{{range .Config.Env}}{{println .}}{{end}}' agent2api |
  sed -n '/^AGENT2API_ACCOUNT_KEY=/p' > "$MIGRATION_DIR/account-key.env"

docker stop --time 60 agent2api
cp -a -- "$SOURCE_DATA/." "$FORK_DATA/"
tar --numeric-owner -cpf "$MIGRATION_DIR/data-before-fork.tar" -C "$FORK_DATA" .
tar -tf "$MIGRATION_DIR/data-before-fork.tar" >/dev/null
docker rename agent2api "$OLD_CONTAINER"
docker run -d --name agent2api --restart unless-stopped \
  -p 3065:3065 \
  --env-file "$MIGRATION_DIR/account-key.env" \
  -e AGENT2API_SELF_UPDATE=0 \
  -e AGENT2API_CAPTCHA_ENABLED=1 \
  -v "$FORK_DATA:/data" \
  "$NEW_IMAGE"
printf 'old_container=%s\nmigration_dir=%s\n' "$OLD_CONTAINER" "$MIGRATION_DIR"
```

마지막에 출력되는 `migration_dir`를 기록하세요. 복사나 아카이브가 실패하면 기존 컨테이너 이름은 아직 바뀌지 않았으므로 `docker start agent2api`로 복구하고 원인을 확인하세요. 이후 교체 명령은 실행하지 마세요. 기존 컨테이너를 보존하면 쓰기 가능 레이어도 유지됩니다. 패널에서 내부 업데이트를 했다면 이전 이미지 태그를 다시 pull하는 것보다 원래 프로그램을 정확히 복원할 수 있습니다.

시작 후 `/health`와 패널의 계정, 자격 증명, 게이트웨이 Key, 플러그인 및 라우팅 그룹을 확인하세요. 계정과 Key는 유지되고 기존 관리형 공개 모델은 위의 설명대로 그룹으로 이전됩니다. 업스트림 목록은 소스만 관리하며 모델을 자동 공개하지 않습니다. 라우팅에서 이전 결과를 확인하고 필요에 따라 그룹을 만들거나 활성화하세요. 기존 모델 ID와 Key로 실제 요청을 검증하세요. 상태 확인만으로 복구를 확인할 수 없습니다. 이후에도 출력된 디렉터리의 `data` 마운트와 `AGENT2API_SELF_UPDATE=0`을 유지하세요.

롤백할 때 이전 디렉터리 자리표시자를 기록한 경로로 바꾸세요. 새 컨테이너를 중지한 다음 보존한 기존 컨테이너를 시작합니다. 원본 데이터는 fork가 업그레이드하지 않았으므로 데이터베이스를 덮어쓸 필요가 없습니다:

```bash
set -euo pipefail
MIGRATION_DIR='/opt/agent2api/migrations/<MIGRATION_TIMESTAMP>'
OLD_CONTAINER=$(cat "$MIGRATION_DIR/old-container-name.txt")
docker container inspect "$OLD_CONTAINER" >/dev/null
STAMP=$(date +%Y%m%d-%H%M%S)
if docker container inspect agent2api >/dev/null 2>&1; then
  docker stop --time 60 agent2api
  docker rename agent2api "agent2api-fork-stopped-$STAMP"
fi
docker rename "$OLD_CONTAINER" agent2api
docker start agent2api
```

기존 컨테이너, 원본 데이터 디렉터리, `data-before-fork.tar`, `account-key.env`를 보존하고 두 인스턴스를 동시에 실행하지 마세요. 원본 디렉터리를 직접 업그레이드했다면 이전 이미지만 바꿔서는 안 되며, 업그레이드 전 전체 데이터와 원래 키를 함께 복원해야 합니다. 예를 들어 `3.3.0-beta.5/.6`의 schema 22는 `3.4.2`의 schema 24로 올라가며, 이전 프로그램은 더 높은 버전의 데이터베이스를 거부합니다. Compose에서도 서비스를 중지하고 데이터를 백업 및 별도 디렉터리로 복사한 다음 이미지, 데이터 마운트와 `AGENT2API_SELF_UPDATE`를 변경하세요. 롤백을 위해 원래 Compose 설정도 보관하세요.

### 메모리 사용량

이미지 안의 게이트웨이(Linux 대상)에는 jemalloc 할당자가 내장되어 있습니다. 장시간 실행과 다계정 동시 포워딩에서 시스템 기본 할당자보다 메모리 단편화가 덜 생기고 RSS도 천천히 늘어나는 일이 줄어듭니다 —— 소형 메모리 머신이 가장 자주 눌리거나 OOM 으로 죽는 지점이 바로 여기입니다.

소형 머신에서는 컨테이너에 메모리 상한을 두는 것을 권합니다. 초과하면 커널이 프로세스를 종료하고 `restart: unless-stopped` 가 다시 띄웁니다. 호스트(또는 같은 머신의 다른 서비스)를 끌어내리는 대신 "한 번 재시작"으로 끝납니다.

```bash
# docker run
docker run -d --name agent2api --restart unless-stopped --memory=1g \
  -p 3065:3065 -v ./data:/data \
  ghcr.io/shifuf/agent2api:latest
```

compose 사용자는 서비스에 `mem_limit: 1g` 한 줄을 추가하세요(`docker-compose.yml` 에 주석 예시가 있습니다). swarm 또는 `docker compose --compatibility` 에서는 `deploy.resources.limits.memory` 를 씁니다. 1g 는 출발점일 뿐이며 실제 동시 처리량에 맞춰 조정하세요.

메모리에 상주하는 두 이미지 캐시 상한은 모두 환경 변수로 줄일 수 있습니다(기본 각 `128` MiB): `AGENT2API_IMAGE_CACHE_MB`(생성 이미지 다운로드 캐시), `AGENT2API_IMAGE_COMPRESS_CACHE_MB`(세션 이미지 압축 결과 캐시). 잘못된 값이나 범위 밖 값은 기본값으로 폴백하며 서비스 시작을 막지 않습니다.

`MALLOC_ARENA_MAX=2` 같은 glibc 할당자 튜닝은 **jemalloc 을 내장하지 않은 형태**(구버전 이미지, 직접 빌드한 서버, 데스크톱)에만 의미가 있습니다. 이 이미지에는 설정할 필요가 없습니다.

**웹 패널 기능 차이**( 이 PC에 데스크톱 클라이언트가 없음에서 비롯됩니다): 웹 로그인(WorkBuddy / Qoder / Cline), SMS 인증 코드, 자격 증명 붙여넣기는 완전히 사용 가능합니다. 이 PC 콜백이 필요한 웹 로그인(AutoClaw / CatPaw / Accio / CodeArts / Trae)과 "이 PC 로그인 상태 가져오기"는 사용할 수 없으니 자격 증명 붙여넣기를 쓰세요. 데스크톱에서 "웹 관리 패널도 공개"를 켠 뒤 브라우저로 열어도 같은 차이가 적용됩니다 —— 동일한 화면, 동일한 판정입니다.

### 컨테이너 내 업데이트(선택)

이 fork의 기본값은 `AGENT2API_SELF_UPDATE=0`입니다. `docker compose up -d --pull always --no-build`로 업데이트하며 `./data`를 유지합니다. 실행 코드가 이미지 태그와 일치하고 자체 기능이 상위 Release로 바뀌는 일을 방지합니다.

컨테이너 내부 업데이트가 필요하면 `AGENT2API_SELF_UPDATE=1`을 명시하고 `WORKBUDDY_UPDATE_REPO` / `WORKBUDDY_UPDATE_API_BASE`를 자체 배포 소스로 설정하세요. 패널이 `agent2api-server-linux-<arch>.tar.gz`를 내려받아 `.sha256`을 검증하고 실행 파일과 `ui/`를 교체한 후 restart 정책으로 새 프로세스를 시작합니다.

같은 `agent2api-server-linux-<arch>.tar.gz` 는 [Linux 서버](#linux-systemd) 의 설치 패키지이기도 합니다: 안의 `agent2api-server` 와 `ui/` 가 이 업데이트 경로가 이름으로 가져가는 항목이고, `install.sh` / `agent2api.service` / `agent2api.env.example` 도 함께 들어 있습니다. 업데이트 경로는 앞의 두 항목만 읽고 나머지는 버리므로(`selfupdate::extract_bundle` 참고), 하나의 산출물이 두 용도를 겸합니다 —— 컨테이너에서는 풀어서 교체, 베어메탈에서는 풀어서 `install.sh` 실행.

주의할 점: 컨테이너 내 업데이트 후에는 이미지 태그와 **실제 실행 중인 버전이 어긋납니다**(`docker inspect`에는 여전히 이전 태그가 표시됩니다). `docker compose pull && up -d`로 컨테이너를 재생성하면 이미지에 포함된 버전으로 되돌아갑니다. 버전을 고정하려면 이 진입점을 켜지 마세요.

## 확인과 클라이언트 연결

게이트웨이가 뜨면 curl로 연결을 확인합니다(`model`에는 `GET /v1/models`에 실제로 있는 이름을 넣으세요):

```bash
curl http://127.0.0.1:3065/health
curl http://127.0.0.1:3065/v1/models

curl http://127.0.0.1:3065/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"deepseek-v4.1-flash","messages":[{"role":"user","content":"你好"}],"stream":true}'
```

클라이언트 연동 예시(Python SDK):

```python
from openai import OpenAI

client = OpenAI(base_url="http://127.0.0.1:3065/v1", api_key="sk-local")
resp = client.chat.completions.create(
    model="deepseek-v4.1-flash",     # 목록에 있는 아무 프로바이더의 모델 — GET /v1/models 참고
    messages=[{"role": "user", "content": "你好"}],
)
print(resp.choices[0].message.content)
```

**브라우저에서 도는 페이지**(자체 제작 Web UI 등)가 `fetch`로 바로 붙으면 교차 출처 프리플라이트에 거부됩니다 — 게이트웨이는 기본적으로 CORS에 응답하지 않아 프리플라이트가 API 키 검사에 걸려 401이 됩니다. 해법: ① 설정의 "보안 → 게이트웨이 교차 출처 접근"을 켜기(출처 `*`. 어떤 웹 페이지든 이 PC 게이트웨이를 두드릴 수 있으므로 "게이트웨이 키"도 함께 설정하세요); ② 페이지를 게이트웨이와 동일 출처로 — 로컬 정적 서버가 페이지를 제공하고 `/v1`을 `127.0.0.1:3065`로 리버스 프록시.

## 네트워크 접근

데스크톱 앱은 기본적으로 `127.0.0.1`에서만 수신합니다. "설정 → 게이트웨이 → 네트워크 접근"에서 "다른 기기의 게이트웨이 접근 허용"을 켜면 모든 IPv4 인터페이스(`0.0.0.0`)에서 수신합니다. **LAN으로 접근을 제한하는 기능도, 인터넷에 자동 공개하는 기능도 아닙니다**. 실제 접근 범위는 라우팅, 포트 전달, 방화벽 설정에 따라 달라집니다. 화면에는 이 기기의 API 주소와 웹 관리 주소를 따로 표시합니다. 접속하는 기기에서 연결할 수 있는 주소를 사용하세요. 표시된 주소가 인터넷 접근을 보장하지는 않습니다. 먼저 패널 관리자를 등록해야 합니다. 관리 API에는 관리자 세션 또는 게이트웨이 키가, API 호출에는 활성화된 게이트웨이 키가 필요합니다. 키가 없으면 기본 키를 자동으로 생성합니다. 웹 관리 패널은 기본적으로 꺼져 있습니다. 어느 스위치든 변경 후 앱을 다시 시작해야 합니다.

데스크톱 설치 패키지에는 웹 패널의 `ui/` 리소스가 포함되어 있습니다. "웹 관리 패널도 공개"를 켜면 게이트웨이에 연결할 수 있는 기기의 브라우저에서 로그인하여 관리할 수 있습니다. 접근 범위는 게이트웨이와 같습니다. 끄면 웹 화면 제공만 중단되며 API 전달과 로컬 데스크톱 관리에는 영향이 없습니다. **데스크톱 창은 독립된 로컬 세션을 사용하므로 별도의 웹 로그인이 필요 없습니다**. 브라우저에서 패널에 접근할 때는 관리자 로그인이 필요합니다.

## 모바일

모바일은 세 가지 형태가 있습니다. 필요에 따라 고르세요:

| 형태 | 설치 방법 | 적합한 용도 |
| --- | --- | --- |
| **브라우저 / PWA** | 휴대폰 브라우저에서 `/m` 열기, "홈 화면에 추가" 가능 | 잠깐 보기, 아무것도 설치하지 않기, iPhone이라면 이게 가장 간편 |
| **Android APK** | [공식 다운로드](https://agent2api.dev/downloads) 또는 Release에서 `Agent2API-<버전>.apk` 설치 | 아이콘, 전체 화면, 여러 서버 관리 |
| **iOS IPA** | [공식 다운로드](https://agent2api.dev/downloads) 또는 Release에서 `Agent2API-<버전>.ipa` 설치(미서명, 직접 재서명 필요) | 아이콘, 전체 화면 |

셋 다 같은 UI 코드입니다. 차이는 "누가 페이지를 제공하는가"입니다: PWA는 게이트웨이가 제공하므로("웹 관리 패널도 공개"가 필수) `/m`이 게이트웨이에서 나오고, APK / IPA는 UI를 패키지에 넣으므로(오프라인에서도 UI가 뜨고 그 스위치가 필요 없음) 동작이 다릅니다.

### 사전 조건 (형태별)

**데스크톱(Windows / macOS / Linux)**: 먼저 네트워크 접근을 켜세요. 브라우저 / PWA는 웹 관리 패널도 켜야 합니다.

1. "설정 → 게이트웨이 → 네트워크 접근 → 다른 기기의 게이트웨이 접근 허용" — 다른 기기의 연결을 허용하며 실제 범위는 네트워크와 방화벽에 따라 달라집니다. 먼저 패널 관리자를 등록해야 하고, 활성화된 게이트웨이 키가 없으면 기본 키를 자동으로 생성합니다.
2. "설정 → 게이트웨이 → 네트워크 접근 → 웹 관리 패널도 공개" — `ui/` 정적 폴더를 제공합니다. **브라우저 / PWA 형태에는 필수** (`/m`은 게이트웨이가 제공하므로 이 스위치가 꺼져 있으면 404). **APK / IPA에는 필요 없음** (UI는 패키지 안에 있음). 다만 1번 스위치는 필요합니다 — 그렇지 않으면 게이트웨이가 `127.0.0.1`만 수신해 휴대폰에서 접근할 수 없습니다.

둘 다 재시작 후 적용됩니다.

**서버 / Docker**: 추가 스위치가 필요 없습니다 — 두 형태 모두 기본적으로 모든 어댑터에서 수신하고 `ui/`를 제공합니다 (Dockerfile에 `AGENT2API_UI_DIR=/app/ui`가 고정되어 있습니다). 컨테이너 또는 서비스 포트가 LAN에서 접근 가능하면 됩니다. `AGENT2API_HOST=127.0.0.1`을 직접 설정했다면 `0.0.0.0`으로 바꾸세요. `AGENT2API_UI_DIR`이 존재하지 않는 디렉터리를 가리키면 패널은 404가 되지만 API는 계속 동작합니다.

### 휴대폰에서 열기 (브라우저 / PWA)

`http://<게이트웨이가 실행되는 기기의 LAN IP>:3065/m`

데스크톱에서는 위 설정 화면에 표시되는 주소(예: `192.168.1.23`)의 끝 `/v1`을 `/m`으로 바꿉니다. Docker / 서버는 호스트의 LAN IP와 매핑된 포트를 사용합니다.

처음 방문하면 로그인 페이지로 이동하며, 패널 관리자로 로그인하면 자동으로 모바일 UI로 돌아옵니다. 관리자가 아직 없으면 로그인 페이지에서 생성을 요청합니다.

### APK 설치 (Android)

처음 실행하면 "서버" 화면이 나옵니다. 단계는 세 가지입니다:

1. "추가"를 눌러 게이트웨이의 `IP 또는 도메인:포트`를 입력합니다 (예: `192.168.1.23:3065`). 프로토콜은 `http://` 또는 `https://`를 쓸 수 있으며(생략 시 http), 포트를 생략하면 http는 3065, https는 표준 443이 됩니다;
2. "연결 후 저장"을 누릅니다 — 먼저 연결을 확인하므로 주소 오류나 네트워크 접근 미설정을 그 자리에서 알 수 있습니다;
3. 로그인 페이지가 뜹니다. 이 게이트웨이의 관리자 계정과 비밀번호를 입력합니다 (관리자가 없으면 "관리자 계정 만들기"가 됩니다).

**여러 서버**: "추가"를 한 번 더 누르면 됩니다. 로그인 상태는 서버마다 따로 저장되므로 전환해도 재로그인이 필요 없고, 돌아와도 마찬가지입니다. 진입점은 "설정 → 서버"이며 목록의 행을 누르면 전환됩니다. **로그인 페이지 하단에도 "다른 서버로 전환"** 이 있어, 로그아웃(또는 세션 만료) 후 목록에 가기 위해 다시 로그인할 필요가 없습니다.

**APK의 알려진 제한**:

- 프로토콜을 쓰지 않으면 `http://` LAN 주소에 평문으로 접속합니다. 위험은 "같은 LAN에서 도청 가능"이며, 게이트웨이 자체는 관리자 로그인을 요구합니다. 없애려면 게이트웨이에 TLS를 설정하고(리버스 프록시나 터널도 가능) App에 `https://` 주소를 입력하세요 — 프로토콜은 입력한 그대로 유지되며, 인증서가 유효하지 않으면 연결 확인이 바로 실패합니다.
- UI는 APK 버전을 따르며 게이트웨이 업그레이드를 따라가지 않습니다. 게이트웨이 업그레이드로 새 화면이 생겼다면 그걸 보려면 새 APK가 필요합니다 (데이터 변화는 영향 없음).

### IPA 설치 (iOS)

Release의 `Agent2API-<버전>.ipa`는 **기본이 미서명 패키지**입니다 — Apple은 개발자가 설치 가능한 앱을 자유롭게 배포하는 것을 허용하지 않으므로, 미서명 패키지는 자신의 Apple ID로 한 번 재서명해야 합니다. 세 가지 경로가 있습니다:

| 방법 | 필요한 것 | 유효 기간 |
| --- | --- | --- |
| **AltStore / SideStore / Sideloadly** | PC(최초 1회) + 무료 Apple ID | 7일, 이후 재서명 |
| **Apple Developer Program** | 연 $99, 자체 인증서와 프로비저닝 프로파일 | 1년 |
| **App Store / TestFlight** | 연 $99 + 심사 | 장기 |

사이드로드 방법: `.ipa`를 AltStore(또는 SideStore)에 끌어다 놓고 Apple ID로 재서명한 뒤 설치합니다. 무료 계정 제한은 "동시에 3개 앱", "7일마다 재서명"입니다.

**iPhone에서 게이트웨이를 잠깐 보는 것뿐이라면 Safari로 `/m`을 열고 "홈 화면에 추가"만 하면 충분**합니다 — IPA를 설치할 필요도, 재서명할 필요도 없습니다.

**IPA의 알려진 제한**:

- **앱 내 업데이트는 다운로드 안내로 연결**: iOS는 앱이 실행 코드를 직접 내려받아 설치하는 것을 허용하지 않으므로, 설정의 "업데이트 확인"에서는 "IPA 다운로드"(공식 CDN에서 `.ipa`를 받아 AltStore / SideStore 또는 자체 인증서로 재서명) 및 공식 다운로드 페이지 링크를 제공합니다(Android처럼 앱 내부에서 바로 설치하지 않음). PWA 형태는 Service Worker로 갱신되므로 새로고침하면 됩니다.
- 평문 `http://` 게이트웨이: `Info.plist`에서 ATS 평문 제한을 풀고 로컬 네트워크 용도도 선언해 두었습니다. 첫 연결 시 "로컬 네트워크 접근 허용" 대화상자가 뜨면 반드시 허용해야 합니다 — 거부하면 모든 요청이 아무 설명 없이 실패합니다.
- 나머지는 APK와 같습니다: UI는 패키지 버전을 따르고 기본 프로토콜은 http입니다.

### 홈 화면에 추가 (브라우저 / PWA)

선택 — 주소 표시줄 없는 전체 화면이 됩니다. 모바일 UI의 "설정 → 앱으로 설치"에 바로 진입점이 있습니다:

- **Android / Chrome**: 설정 페이지에서 "홈 화면에 추가"를 탭하면 시스템 설치 대화상자가 열립니다. 메뉴 → "홈 화면에 추가" / "앱 설치"로도 가능합니다
- **iOS / Safari**: Safari에는 설치 API가 없어 설정 페이지에 절차를 적어 두었습니다 — 공유 → "홈 화면에 추가"

홈 화면 아이콘으로 열면 모바일 홈 페이지로 바로 이동합니다. 이미 독립 창에서 실행 중이면 설정 페이지에 "설치됨"이 표시됩니다.

새 버전이 있으면 화면 하단에 "재시작 후 업데이트" 바가 뜹니다. 게이트웨이 업그레이드 후 새 UI는 이미 내려받아져 있고, 한 번 누르면 전환됩니다(무시해도 현재 사용에는 영향이 없고 다음 실행 시 적용됩니다).

> **네이티브 앱 / 스토어 패키지가 없는 이유**: 모바일 UI는 항상 **다른 기기에서 실행되는 게이트웨이**에 연결합니다 (게이트웨이는 그 기기의 클라이언트 로그인을 읽고 설정 파일을 써야 하므로 휴대폰에서는 실행할 수 없습니다). 본질은 "HTTP 서비스에 대한 원격 접근"이며 브라우저가 가장 적합한 매체입니다 — 동일 출처 인증, 설치 불필요, 게이트웨이와 함께 업그레이드됩니다. PWA 형태는 전체 화면과 홈 화면 아이콘을 추가로 제공해 네이티브 앱과 같은 사용감을 줍니다.
>
> **Service Worker(오프라인 셸)는 `https` 또는 `localhost`에서만 동작합니다**: LAN 접근은 `http://<IP>`이므로 브라우저가 SW를 제공하지 않아 오프라인일 때 모바일 UI를 열 수 없습니다. 이는 브라우저의 보안 제한이며 기능 부재가 아닙니다 — 정상 사용 시 게이트웨이가 온라인이므로 영향이 없습니다.

### 플러그인 및 예약 작업 런타임

플러그인 화면에서 호환되는 Magpie / OpenCode v1 패키지를 직접 설치하고 Bun 1.4.2 다운로드 상태를 확인할 수 있습니다. 필요할 때 런타임을 다운로드하고 검증하며 여러 플러그인이 하나의 Bun 프로세스를 공유합니다. 전체 설치 및 실행을 지원하므로 이전 커뮤니티 보관 파일의 QEMU 진단 절차는 사용하지 않습니다.

예약 작업은 내장 QuickJS를 사용하므로 Node.js나 Bun을 따로 설치할 필요가 없습니다. 스크립트는 플러그인이 선언한 도메인 범위에서 전체 HTTP를 사용할 수 있습니다. 모든 리디렉션을 검증하며 로컬 및 사설 네트워크 주소는 차단합니다. 알림은 플러그인 선언과 사용자 허가가 모두 필요합니다. 작업은 선택한 프록시를 사용하며 프록시 실패 시 직접 연결로 전환하지 않습니다. 활성화하거나 수동 실행하기 전에 화면에서 설정과 권한을 확인하세요.

### WebDAV 또는 S3에서 계정 키 복원

클라우드 동기화는 로컬 계정 키가 없을 때만 원격 키를 설치합니다. 기존 `account.key` 또는 유효한 `AGENT2API_ACCOUNT_KEY`와 같으면 변경하지 않습니다. 키가 다르면 스냅샷에 포함되지 않는 로컬 데이터를 보호하기 위해 가져오기를 거부합니다. 새 데이터 디렉터리에 복원하거나 암호화된 전체 백업을 사용해 이전하고, 기존 키를 삭제하지 마세요.

### 선택 사항: 패널 로그인용 OAuth 및 Cloudflare Turnstile

새 업스트림 기능은 데스크톱의 설정 → 계정 → 외부 로그인과 모바일의 설정 → 외부 로그인 (OAuth)에 있습니다. 관리자를 등록한 뒤 Google / GitHub client ID, secret과 패널 외부 주소를 설정하세요. 역방향 프록시에서는 고정 HTTPS 주소를 사용하고 공통 콜백 `/api/panel/oauth/callback`을 등록합니다. 계정을 연결하거나 Google의 확인된 이메일 / GitHub 사용자 이름 허용 목록을 설정할 수 있습니다. 웹은 같은 탭에서 이동하고 데스크톱 셸·모바일 앱은 외부 브라우저를 열어 결과를 폴링한 뒤 짧은 일회용 티켓을 관리자 세션으로 교환합니다. 아래 기존 설정과는 독립적입니다.

기존 설정은 데스크톱의 설정 → 계정 → 기존 로그인 설정에 남으며 모바일에도 해당 편집기가 있습니다. 기존 OAuth는 직접 관리하는 고정 HTTPS 출처, `/api/panel/oauth/{google|github}/callback`과 같은 출처의 관리자 브라우저 Cookie를 통한 명시적 연결이 필요합니다. Google `sub` / GitHub 숫자 `id`만 인정하며 이메일 일치로 권한을 주지 않습니다. 출처나 client ID를 바꾸면 연결이 해제됩니다. 기존 방식은 네이티브 셸, APK, Cookie 차단 중계에 로그인 티켓을 전달하지 않으므로 비밀번호를 사용하거나 새 방식을 별도로 설정하세요. 두 설정과 연결은 자동 이전되거나 서로 덮어쓰지 않습니다. OAuth·인증 설정과 브랜딩 쓰기에는 관리자 세션이 필요하며 일반 게이트웨이 Key로 로그인 방식을 설정할 수 없습니다.

새 설정 → 계정 → 봇 인증은 모바일에도 있으며 ALTCHA 또는 같은 출처의 Turnstile과 데스크톱·웹 개별 스위치를 지원합니다. 허용 호스트에는 실제 위젯 호스트 이름을 입력하세요. 새 인증 제공자 설정을 저장하기 전에는 기존 설정이 유지되고 저장하면 새 설정이 적용됩니다. 데스크톱이나 웹 스위치만 변경해도 제공자가 전환되지는 않습니다. 아래 별도 정적 사이트 절차는 기존 로그인 설정의 이전 Turnstile에만 해당합니다.

기본 ALTCHA는 외부 서비스가 필요 없습니다. Turnstile에는 **직접 관리하는 별도의 HTTPS 정적 사이트**가 필요합니다. 패널이나 게이트웨이의 호스트 이름을 사용하거나, 이 사이트에서 API를 프록시하거나 패널 쿠키와 인증 정보를 저장하지 마세요.

1. 패널의 `/api/panel/turnstile-widget`에서 HTML을 다운로드합니다. 정적 사이트의 `/turnstile-widget.html`에서 원본 그대로 `text/html`로 제공하고 패널의 삽입을 허용하세요. 패널 다운로드 URL은 iframe URL이 아닙니다.
2. Cloudflare에서 Turnstile 위젯을 만들고 패널이 아닌 **정적 사이트의 호스트 이름**을 허용하세요. 클라이언트는 정적 사이트와 `challenges.cloudflare.com`에, 게이트웨이는 후자에 HTTPS로 연결할 수 있어야 합니다.
3. 관리자 세션을 열어 둔 채 설정 → 계정 → 기존 로그인 설정 → 로그인 인증 방식에서 Turnstile을 선택합니다. site key, secret key, 정적 사이트의 `https://호스트이름`(포트·경로 제외)을 입력하고 이 배포 환경의 인증 스위치를 켠 뒤 시크릿 창에서 비밀번호 로그인을 테스트하세요.

서버는 인증 성공, 정확한 정적 호스트 이름, `action=agent2api_panel`을 모두 확인합니다. 통신 또는 인증 실패 시 검증을 건너뛰거나 ALTCHA로 전환하지 않습니다. 열어 둔 관리자 세션에서 ALTCHA로 되돌릴 수 있습니다. Cloudflare 공개 테스트 키는 필수 action을 반환하지 않아 운영 로그인 검증에 사용할 수 없습니다.
